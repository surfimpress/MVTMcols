# Refactor 1 — Recommendations

This document lists ONLY low-risk simple improvements drawn from the baseline audit. Each item has a category, a one-line rationale, and a risk note. Performance, architecture, and large refactors are deliberately out of scope.

Risk levels used below:
- **Trivial** — pure cleanup, won't change runtime behaviour, very small blast radius
- **Low** — a real change but the affected surface is a single helper or constant
- **Caution** — touches behaviour-bearing code or schema; needs verification before action

> **Audit-correction notice (added after the fact).**
> Sections A, B, C below contain a small number of items I asserted on the basis of a quick read rather than verification. Each affected item is left in place and followed by a `↳ Correction` paragraph that states what I got wrong, what is actually true, and what would have caught the error in one tool call. The point of leaving the wrong text visible is to make the gap between "looks plausible from a name" and "verified from the code" inspectable, so future audits start by *grepping* and not by *recognising*.

↳ **Correction to C2 — original recommendation was wrong on Python 3.9.** The literal advice "wrap each in `with sqlite3.connect(...) as conn:`" does not do what it sounds like on the deployment target. In Python 3.9 (and 3.10, 3.11), `with conn:` is a *transaction* context manager — it commits on success, rollbacks on exception, but does **not** close the connection. Auto-close on `__exit__` was added in Python 3.12. So the literal recommendation would have left the connection-leak risk unfixed on the box this code actually runs on. **Why I got this wrong:** I assumed `with sqlite3.connect(...) as conn:` did what equivalent `with open(...) as f:` does. It doesn't. The 3.9-correct idiom is `with closing(sqlite3.connect(db_path)) as conn, conn:` — which is what landed in commit `6d6b8e7`. **What would have caught it:** running the recommendation past `python --version` and a one-line check of the `sqlite3` docs for the target Python. Same flavour of mistake as the `zip(strict=)` issue earlier in this branch — assuming "the natural Python idiom" works on a Python that's actually three years old.

## Risk assessment

**Cross-cutting risks to be aware of in any refactor:**

1. **Shared PDF helpers** (`_open_clean`, render-to-grey) — five copies exist because each detector evolved independently. Before consolidating, render the same page through each version and `numpy.array_equal` the results. A subtle difference in pixmap mode (RGB vs RGBA, or `pix.n` handling) will silently change downstream contour results.

2. **DPI constants** — different stages use different DPIs intentionally (column detection at 450, ad detection at 150). Centralizing is fine but **uniforming** is not. Use named constants like `COLUMN_DPI`, `AD_DPI`, never a single `DEFAULT_DPI`.

3. **`page_layouts.confidence` and other stored derived values** — if any centralization changes how a constant is computed, persisted DB rows will be inconsistent with newly-written ones. Check the populate path before changing the input constant.

4. **Dynamic imports** in `process_issue.py` — `LayoutDB`, `validate_columns`, `detect_headlines`, `detect_body_text` are imported inside functions, not at module top. A static-analysis tool may report them as unused; don't believe it.

5. **No commit on this branch should land without a behaviour-equivalence rerun.** Re-run the same four sample issues (1898-10-07, 1920-01-02, 1937-01-14, 1947-11-06) and diff `detected_ads` and `page_layouts` row counts pre/post each cleanup commit. The plumbing for that is already proven.

## Defensive preservation — recap for any future refactor commit

For each subsequent commit in this refactor branch (e.g. B1–C2 from the table above), repeat this pattern:
- Snapshot anything non-git that's about to change (DB → `data/mvtm.db.pre-<step>.bak`).
- Make ONE small focused change. Don't batch.
- Run the four-issue verification.
- Commit + push immediately. Don't accumulate.
- If the machine dies, only the in-flight unit is at risk.

## Opportunities (low-effort signals, no deep dive)

1. **`coordinates.py` is only used by `detect_body_text.py`.** Either expand its use across the other detectors (good) or fold it into the consumer (also fine). Either way, current state is asymmetric.

2. **~~`page_meta.json` and `page_analysis.json` overlap.~~ — Struck on assessment.** The original framing ("both contain column data") was wrong. On inspection: field overlap is essentially zero. `page_meta.json` (~1.8 KB) holds the placed-column result (`columns[]`, `num_columns`, `image_path`s, `quality_flags`). `page_analysis.json` (~168 KB, ~90× bigger) holds the diagnostic dump (`profile_chart`, `strip_profiles`, `composite_profile`, `detected_boundaries`, plus runtime-added `body_text_charts`, `headlines`, `single_col_ads`, `r2`, `r3`). The two are complementary — result vs trace — with very different lifecycles (page_meta written when columns are extracted; page_analysis rewritten every pipeline run, viewer fetches it with a cache-buster). Merging would smear that result/diagnostics boundary, force every small read site (`detect_body_text.py:26`) to load 168 KB to get the columns array, and couple two failure modes that today degrade independently. **Why I got the original framing wrong:** I scanned the file names and the orchestrator role ("both per-page, both fed to the viewer") and inferred overlap without opening the schemas. The 90× size asymmetry alone should have prompted a closer look. **Lesson:** when an audit claims two outputs "overlap," dump both schemas before recommending a merge — same flavour as the C1 lesson about rendering function bodies side by side.

3. **~~`viewer.py` hardcoded `BASE = '/MVTM/columns'` mirrored in `page_viewer.html`.~~ — Struck on assessment.** Only two literals are actually hand-maintained: `viewer.py:20` (`base_url="/MVTM"` — the parent of `/columns/`) and `page_viewer.html:194` (`/MVTM/columns` — the full path). `viewer.html`'s `BASE` is regenerated every `viewer.py` run, so not a drift risk. Centralisation options were (a) build-time substitution into `page_viewer.html`, which turns a hand-edited file into a build artefact, or (b) a runtime `fetch('/MVTM/viewer_config.json')` adding a 1-RTT delay and a new failure mode (config fetch fails → blank viewer). The parent-vs-full-path asymmetry between the two literals also makes a single constant awkward — every callsite would have to decide to append or strip `/columns/`. **Cost/benefit:** the path has been `/MVTM/` for the life of the project; if it ever moves the fix is three lines across three files, immediately obvious from broken images. Permanent infrastructure to prevent a one-time edit isn't worth it.

The 21 rows are all `/tmp/...` paths dated 2026-04-11 — CLI invocations from the strip-consensus / era-test development work. The original framing ("*either* we stopped logging *or* it's only populated on a debug path") straddled both halves of the truth: the CLI still logs (we haven't stopped); the production pipeline never did (so it is "debug-path only" in the sense that `process_issue` writes via `LayoutDB.record_layout` to `page_layouts` and never touches `page_splits`). The table is doing exactly what `_log_to_db` documents — benignly idle, no bloat risk. Any future deletion of `page_splits` should land as part of the broader CLI consolidation (opp #9), not as a standalone.

5. **~~`store_ads` returns ids; `record_layout` could too.~~ — Struck on assessment.** The framing rests on a SELECT-to-drop that doesn't exist. `store_ads` returns ids because `process_issue` immediately attaches each id to the RGBA cutout in `extract_columns(...)` so the page viewer can link clipped regions back to ad rows — a real per-row coupling. `record_layout` has no analogous downstream consumer (grep confirms zero references to a `page_layouts.id` anywhere in the codebase). The "SELECT" the opportunity says symmetry would drop is in `_update_viewer_data`, but that function rebuilds the *entire* viewer JSON for *all* issues by SELECTing the whole `page_layouts`/`page_geometry`/`detected_ads` corpus — it doesn't read back recently-inserted rows. Returning an unused id from `record_layout` would add API surface that tempts a future caller to invent a coupling that doesn't currently exist, *increasing* complexity rather than reducing it.

6. **~~`detected_ads.cols` vs `page_layouts.num_columns`~~ — Struck on assessment.** These are not the same concept. `detected_ads.cols` is a **per-rectangle column span** (this ad spans N columns), computed at detect_ads.py:158 as `round(bw / w * 100 / pitch)`. `page_layouts.num_columns` is a **per-page total** (this page has N columns). A clarity rename `cols` → `cols_spanned` would be small (~5 touchpoints + a `RENAME COLUMN`) but unjustified for refactor-1: the field has worked under its current name for the life of the project, no observed confusion, and a clarity-only rename without a triggering need is exactly the accretive change the standing feedback warns against.
